# Platform research snapshot (2026-10-05)

Evidence base for `docs/ARCHITECTURE.md` and `docs/adr/0001-platform-stack.md`. Six research topics were investigated against primary sources on 2026-10-05. Every fact carries the confidence its researcher assigned: `verified` (confirmed at the cited source), `likely` (secondary or indirect evidence) or `unverified` (an estimate, or no source found). The architecture cites these as [R-v], [R-l] and [R-u] and never upgrades a label.

This is a point-in-time snapshot. Versions move; exact pins live in Git and are maintained by Renovate. Do not edit facts here: supersede them with a new dated snapshot.

## Node 1 hardware, Proxmox VE and OpenTofu providers

Node 1 is a 2012-era Ivy Bridge desktop platform: an Intel Core i5-3570 (4C/4T, 3.4-3.8 GHz, 77 W TDP, VT-x/EPT/VT-d/AES-NI, SSE4.2+AVX but no AVX2, so x86-64-v2 and NOT v3) on a Gigabyte GA-H61M-S1 whose H61 PCH caps memory at 16 GB (2 DIMMs, 1 DIMM per channel), provides only four SATA 3 Gb/s ports, two PCIe 2.0 x1 slots plus one CPU-fed x16 slot, USB 2.0 only, and no RAID; chipset-level VT-d/IOMMU should be treated as unavailable (no PCIe passthrough), while USB device passthrough still works. The board revisions 2.1/3.0/4.0 carry AMI UEFI firmware, but Proxmox supports both UEFI (systemd-boot/GRUB) and legacy BIOS (GRUB) with ZFS root, so boot mode is not a blocker. Current Proxmox VE is 9.2 (released 2026-05-21, Debian 13.5, Linux 7.0 default kernel with 6.17 as alternative, QEMU 11.0, ZFS 2.4); it requires only a 64-bit VT-x CPU and Debian 13's amd64 baseline is still x86-64-v1, so Ivy Bridge is fully supported. Talos 1.14.x (latest 1.14.2, Kubernetes 1.37.1) requires x86-64-v2, which the i5-3570 satisfies, so the VM CPU type should be 'host' on this single, non-migrating host; PVE's own default x86-64-v2-AES would also boot Talos. Both NICs are Realtek and served by the in-tree r8169 driver (RTL8125 since Linux 5.4, RTL8125B since 5.9); the vendor r8125 DKMS (TP-Link ships one for kernels <= 5.17) is unnecessary and should be avoided, but an unresolved Proxmox kernel 6.17 regression (Bugzilla 7237, RTL8125/RTL8168 negotiating 100 Mbps) means the 2.5 GbE point-to-point link to Node 2 must be validated on the kernel actually deployed (7.0 or pinned 6.14). The 16 GB budget is the hard constraint: PVE host services (~1-1.5 GiB) plus a ZFS ARC pinned at roughly 1-2 GiB leaves about 12 GiB for guests, enough for one Talos control plane (4 GiB) and one or two workers (3-4 GiB each) with ballooning disabled, not for a three-node control plane. Storage is a single 256 GB consumer SATA SSD on a 3 Gb/s port: a single-disk ZFS rpool gives checksums, compression, snapshots and send/receive and can be converted to a mirror later with zpool attach plus proxmox-boot-tool without reinstalling, at the cost of extra write amplification on a consumer drive versus LVM-thin; whichever is chosen must be documented with the wear trade-off. For IaC, bpg/proxmox v0.115.0 (targets PVE 9.x, 9.2 tested, Terraform >= 1.5 / OpenTofu >= 1.6, SDKv2, no 0.x compatibility guarantee) and siderolabs/talos v0.12.0 (Talos SDK 1.14, new talos_machine and talos_cluster resources, ephemeral kubeconfig/talosconfig since 0.11) on OpenTofu 1.13.1 are current; Telmate's provider is still RC-only (3.0.2-rc10) and should not be used. PVE 9 removed the VM.Monitor privilege and introduced VM.GuestAgent.* and VM.Replicate, so least-privilege roles for OpenTofu and for the Proxmox CSI plugin must be built from the PVE 9 privilege list with privilege-separated, expiring API tokens; API tokens cannot upload cloud-init snippets (SSH required), which argues for applying Talos machine config over the Talos API rather than via cicustom snippets, using the Image Factory nocloud image (downloaded as .raw.gz/.raw.zst because PVE's download-url API cannot decompress xz). Proxmox's OpenID Connect realm (issuer URL, client ID/secret, PKCE, username-claim, groups-claim, autocreate) is the documented Authentik integration path for human logins; OIDC does not cover API tokens. Idle wall power for such a system is roughly 25-40 W (estimate), ~0.6-1 kWh/day.

### Facts

- [verified] **GA-H61M-S1 board spec:** GA-H61M-S1 (all listed revisions 2.1/3.0/4.0, and rev 2.0 per Gigabyte spec page): Intel H61 PCH (BD82H61), Socket LGA1155, 2 x DDR3 DIMM slots, max 16 GB, 4 x SATA II (3 Gb/s) ports, 1 x PCIe x16 slot + 2 x PCIe x1 slots, 8 x USB 2.0 (no USB 3.0), micro-ATX 226 x 174 mm; supports Sandy Bridge and Ivy Bridge Core/Pentium/Celeron and Xeon E3-1200 v1. Direct fetch of gigabyte.com returned HTTP 403, so the Gigabyte page could not be read first-hand. <https://theretroweb.com/motherboards/s/gigabyte-ga-h61m-s1-rev-2-1>
- [likely] **GA-H61M-S1 board spec:** Per the Gigabyte rev 2.0 specification page (as indexed) and mobilespecs.net: the x16 slot runs PCIe 3.0 only with a 22 nm Ivy Bridge CPU (PCIe 2.0 with Sandy Bridge), the two x1 slots are PCIe 2.0 (5 GT/s, ~4 Gbit/s usable, sufficient for a 2.5GbE card), memory is 1.5 V DDR3 1333/1066/800 (2200 OC), and the onboard LAN is a Realtek RTL8111F 10/100/1000 chip; USB ports are 2.0 only. <https://www.gigabyte.com/Motherboard/GA-H61M-S1-rev-20/sp>
- [likely] **GA-H61M-S1 firmware / revisions:** Board revisions 2.0, 2.1, 2.2, 3.0 and 4.0 exist (rev 2.2/3.0/4.0 share one manual). The Retro Web lists AMI UEFI firmware for rev 2.1 (BIOS F5-F10b), rev 3.0 (F1-F4) and rev 4.0 (F2-F4); a forum source states rev 2.0 has a single 32 Mbit flash with licensed AMI EFI BIOS and no hardware DualBIOS. UEFI boot is therefore probable but is an early (2012) AMI implementation; the exact revision and BIOS version on the user's board are unknown. <https://theretroweb.com/motherboards/s/gigabyte-ga-h61m-s1-rev-3-0>
- [verified] **Intel H61 PCH capabilities:** Intel 6 Series datasheet (324645-006) Table 1-2, H61 column: 6 PCIe 2.0 ports (ports 7-8 disabled), no PCI interface, 10 USB 2.0 ports, 4 SATA ports total of which 0 are 6 Gb/s and 4 are 3 Gb/s (ports 2-3 disabled), RAID 0/1/5/10 = No, Intel RST SSD caching = No, AHCI listed 'No' with footnote 3 ('PCH provides hardware support for AHCI functionality when enabled by appropriate system configurations and software drivers'); H61 supports only 1 DIMM per channel, which is why the platform maximum is 16 GB although the CPU IMC supports 32 GB. <https://www.intel.com/content/dam/www/public/us/en/documents/datasheets/6-chipset-c200-chipset-datasheet.pdf>
- [likely] **VT-d / IOMMU on H61:** Intel's ARK page for the H61 Express Chipset has been removed (redirects to a 404 page), so an official VT-d Yes/No could not be retrieved. Wikipedia's list of IOMMU-supporting hardware names Q67, Q77, Z77 etc. but not H61/H67/P67/Z68, and community sources report Intel confirmed VT-d support officially begins with Q67 in the 6-series. The 6-series datasheet describes VT-d as a PCH capability but its SKU table does not differentiate it, and board vendors generally do not expose VT-d on H61 firmware. Conclusion: assume no usable VT-d/IOMMU on Node 1 (the CPU itself lists VT-d: Yes, but chipset+BIOS support is also required). <https://en.wikipedia.org/wiki/List_of_IOMMU-supporting_hardware>
- [verified] **Intel Core i5-3570:** Intel ARK: 4 cores / 4 threads, 3.40 GHz base / 3.80 GHz turbo, 6 MB cache, 77 W TDP, 22 nm Ivy Bridge, launched Q2'12, FCLGA1155, Intel HD Graphics 2500 (650 MHz-1.15 GHz, 3 displays), 2-channel DDR3-1333/1600 (max 32 GB, 25.6 GB/s), PCIe 3.0 with 16 lanes (1x16, 2x8, 1x8+2x4), VT-x Yes, VT-d Yes, EPT Yes, AES-NI Yes, TXT Yes, instruction sets SSE4.1/SSE4.2/AVX; status Discontinued, End of Servicing Lifetime 2019-12-31 (no further microcode/security updates from Intel). <https://www.intel.com/content/www/us/en/products/sku/65702/intel-core-i53570-processor-6m-cache-up-to-3-80-ghz/specifications.html>
- [verified] **x86-64 microarchitecture level:** x86-64-v2 requires CMPXCHG16B, LAHF-SAHF, POPCNT, SSE3, SSSE3, SSE4.1, SSE4.2 (Nehalem-era); x86-64-v3 additionally requires AVX, AVX2, BMI1, BMI2, F16C, FMA, LZCNT, MOVBE, OSXSAVE (Haswell 2013). Ivy Bridge has AVX but not AVX2/BMI/FMA, so the i5-3570 satisfies x86-64-v2 but NOT x86-64-v3; binaries built with -march=x86-64-v3 (or GOAMD64=v3) will crash with SIGILL on this host. <https://en.wikipedia.org/wiki/X86-64#Microarchitecture_levels>
- [verified] **TP-Link TX201 hardware:** TP-Link spec: 1 x PCI Express 2.1 x1 interface, 1 x RJ45, 10/100/1000/2500 Mbps, Windows and Linux listed; hardware versions on the download page are V1 and V1.60. The chip is a Realtek RTL8125-family 2.5GbE controller (PCI ID 10ec:8125; TP-Link's Linux FAQ ships Realtek's r8125 driver for 'RTL8125 2.5Gigabit Ethernet controllers'; Linux users see 'Realtek RTL8125 2.5GbE ... driver: r8169'). Reports of PCI revision 05 indicate the RTL8125B variant, but TP-Link does not publish the exact sub-variant. <https://www.tp-link.com/us/home-networking/pci-adapter/tx201/>
- [verified] **TP-Link TX201 vendor driver:** TP-Link's own Linux driver download for TX201 (published 2024-09-18) states support only up to 'Linux kernal 5.17'; it is the Realtek out-of-tree r8125 package and cannot be built against the 6.8-7.x kernels used by Proxmox VE 8/9 without third-party DKMS forks. It is not needed because the in-tree r8169 driver supports the chip. <https://www.tp-link.com/us/support/download/tx201/>
- [verified] **Linux in-tree r8169 support for RTL8125:** RTL8125 (A) support was added to the in-tree r8169 driver in Linux 5.4 (Nov 2019, LWN 'r8169: add support for RTL8125'); RTL8125B support was added in Linux 5.9 (commit 0439297be951, Oct 2020) with optional rtl8125b firmware in linux-firmware >= 20200721. Every Proxmox VE 8/9 kernel (6.8, 6.14, 6.17, 7.0) therefore includes native support for the TX201 and for the onboard RTL8111F; a separate r8125 DKMS module is unnecessary. <https://bugzilla.redhat.com/show_bug.cgi?id=1854314>
- [verified] **Realtek regression on Proxmox kernel 6.17:** Proxmox Bugzilla #7237 'Realtek 2.5Gbps Ethernet downgraded to 100Mbps with kernel 6.17' (reported 2026-01-14, last update 2026-03-10, status NEW): on PVE 9.1 kernels 6.17.4-2 through 6.17.13-1 some RTL8125 and RTL8168 NICs negotiate only 100 Mbps, with both r8169 and r8125 drivers; reverting to the 6.14 kernel restores full speed. Whether PVE 9.2's kernel 7.0 is affected or fixed is not stated anywhere found [unverified]. <https://bugzilla.proxmox.com/show_bug.cgi?id=7237>
- [likely] **TX201 on Proxmox anecdote:** A Proxmox forum thread (PVE 8.1.3, kernel 6.5.11) reports a TX201 linking at only 100 Mb with r8169; the advice was to build r8125 DKMS using 'proxmox-headers' (the package was renamed from pve-headers with kernel 6.5+). This is a single anecdote on an older kernel; later threads note that with kernel 6.14 the r8125-dkms package should be removed in favour of r8169. <https://forum.proxmox.com/threads/tplink-tx201-unter-proxmox.138811/>
- [verified] **Proxmox VE 9.0 / 9.1 releases:** Proxmox VE 9.0 was released 2025-08-05 on Debian 13 'Trixie' with kernel 6.14.8-2, QEMU 10.0.2, LXC 6.0.4, ZFS 2.3.3, Ceph Squid 19.2.3 (new: snapshots on thick LVM, SDN fabrics, HA affinity rules, ZFS RAIDZ expansion). Proxmox VE 9.1 followed on 2025-11-19 with Debian 13.2, kernel 6.17.2-1, QEMU 10.1.2, LXC 6.0.5, ZFS 2.3.4. <https://www.proxmox.com/en/about/company-details/press-releases/proxmox-virtual-environment-9-0>
- [verified] **Proxmox VE 9.2 (current stable):** Proxmox VE 9.2 was released 2026-05-21 (arm64 build 2026-08-05) and is the current stable release as of 2026-10-05: Debian 13.5, Linux kernel 7.0 as default with 6.17 kept as an alternative, QEMU 11.0, LXC 7.0, ZFS 2.4, Ceph Tentacle 20.2 / Squid 19.2; new dynamic load balancer, custom CPU model management UI/API, HA arm/disarm, SDN WireGuard and BGP fabrics. Linux 7.0 (released 2026-04-12) is simply the successor of 6.19, not an architectural change. <https://proxmox.com/en/about/company-details/press-releases/proxmox-virtual-environment-9-2>
- [verified] **Proxmox VE requirements vs Ivy Bridge:** PVE system requirements: 64-bit Intel 64/AMD64 CPU with Intel VT/AMD-V, minimum 1 GB RAM (evaluation) and recommended at least 2 GB for OS plus guest memory, about 1 GB RAM per TB used for ZFS/Ceph, SSDs with power-loss protection recommended and consumer SSDs discouraged, ZFS/Ceph incompatible with hardware RAID controllers. There is no x86-64-v2 requirement, and Debian 13's amd64 baseline is still plain x86-64 (v1), so PVE 9.x installs and runs on the i5-3570. <https://pve.proxmox.com/wiki/System_Requirements>
- [verified] **Proxmox VE 9 breaking changes affecting IaC roles:** PVE 9.0 removed the VM.Monitor privilege (QEMU HMP access now needs Sys.Audit; guest-agent access uses new VM.GuestAgent.Audit / FileRead / FileWrite / FileSystemMgmt / Unrestricted privileges), added VM.Replicate, requires Sys.Modify to create privileged containers, dropped cgroup v1, dropped GlusterFS, enables intel_iommu by default, and ships AppArmor 4. Custom roles copied from pre-9 blog posts or the Telmate provider (which required VM.Monitor) fail on PVE 9; pve8to9 flags such roles. <https://pve.proxmox.com/wiki/Roadmap>
- [verified] **ZFS ARC sizing on Proxmox:** Since PVE 8.1 the installer sets zfs_arc_max to 10% of host RAM, clamped to a maximum of 16 GiB (about 1.6 GiB on a 16 GB host); the limit is persisted in /etc/modprobe.d/zfs.conf (options zfs zfs_arc_max=<bytes>) and requires 'update-initramfs -u -k all' plus a reboot; if the chosen value is below zfs_arc_min (default 1/32 of RAM) zfs_arc_min must be lowered too. The wiki's general guidance is 2 GiB base + 1 GiB per TiB of storage and ECC RAM, which this consumer board cannot provide. <https://pve.proxmox.com/wiki/ZFS_on_Linux>
- [verified] **Proxmox host bootloader (UEFI vs legacy):** PVE picks the bootloader automatically: legacy BIOS -> GRUB; UEFI + ZFS root without Secure Boot -> systemd-boot; UEFI with Secure Boot or non-ZFS root -> GRUB (EFI). The installer creates a 1 MB BIOS boot partition, an ESP and the OS partition on every selected disk, and proxmox-boot-tool keeps kernels/initrds synchronized to all ESPs ('proxmox-boot-tool format <ESP>' / 'init <ESP>' for a newly added mirror disk). Secure Boot has been supported since PVE 8.1. Hence a legacy-only or flaky-UEFI H61 firmware is not a blocker for ZFS root. <https://pve.proxmox.com/wiki/Host_Bootloader>
- [verified] **Mirroring a single-disk rpool later:** OpenZFS zpool-attach(8): 'If vdev is not currently part of a mirrored configuration, device automatically transforms into a two-way mirror of device and new_device'; the -s flag allows a sequential resilver followed by an automatic scrub. On PVE the procedure is: replicate the partition table to the new disk (sgdisk <healthy> -R <new>; sgdisk -G <new>), zpool attach rpool <old-part3> <new-part3>, then proxmox-boot-tool format/init on the new disk's ESP. No reinstall is required, and the H61 board has three spare SATA 3 Gb/s ports for this. <https://openzfs.github.io/openzfs-docs/man/master/8/zpool-attach.8.html>
- [likely] **LVM-thin vs ZFS on a consumer SSD:** PVE storage table: both LVM-thin and ZFS (local) are stable block-level backends with snapshots and thin provisioning; ZFS additionally offers checksumming, compression, clones, send/receive and PVE storage replication. Community measurements and Proxmox forum threads report ZFS write amplification of roughly 3x to 20x+ on VM workloads (sync writes, no PLP), which wears consumer SSDs noticeably faster than ext4/LVM-thin; mitigations are capping ARC, enabling discard/autotrim, moving logs/RRD/swap off the SSD, and avoiding ZFS-on-ZFS inside guests. <https://pve.proxmox.com/wiki/Storage>
- [verified] **Proxmox QEMU CPU types:** Since PVE 8.0 new VMs default to CPU type x86-64-v2-AES (requires Intel Westmere or newer / AMD Opteron G4), which is strictly older than Ivy Bridge, so it boots Talos; 'host' exposes all host flags (AES-NI, AVX, RDRAND, F16C on Ivy Bridge) for maximum performance and is recommended for homogeneous or single-node setups, its only downside being blocked live migration to different CPUs. kvm64 lacks SSE4.2/POPCNT/CX16 and must not be used for Talos. PVE 9.2 adds GUI/API management of custom CPU models. <https://pve.proxmox.com/wiki/Qemu/KVM_Virtual_Machines>
- [verified] **Proxmox VM disk/controller/firmware recommendations:** PVE docs recommend 'VirtIO SCSI single' with IO Thread for performance (one controller per disk), Discard on thin-provisioned storage so guests can reclaim space, optional SSD emulation, default cache 'none' (writeback risks data loss without a UPS), OVMF (UEFI) when Secure Boot or PCIe passthrough is needed with q35 as the modern machine type, VirtIO paravirtualized NIC with multiqueue equal to vCPU count for busy workloads, and the QEMU guest agent for clean shutdown, freeze/thaw during snapshots and IP reporting. Ballooning is on by default but Talos requires it off. <https://pve.proxmox.com/wiki/Qemu/KVM_Virtual_Machines>
- [verified] **Proxmox OpenID Connect realm:** PVE natively supports OpenID Connect realms: issuer URL, client ID and client key, PKCE, autocreate users, username-claim (subject, username or email), groups-claim with groups-autocreate and groups-overwrite, optional userinfo query; users are created in user.cfg on first login and permissions are assigned via ACLs/groups (OIDC groups get a '-<realm>' suffix). Two-factor options are TOTP, WebAuthn/FIDO2, YubiKey OTP and recovery keys. OIDC is for interactive logins; API automation uses API tokens, and VM/system console endpoints cannot be accessed via tokens. <https://pve.proxmox.com/wiki/User_Management>
- [verified] **Authentik -> Proxmox integration:** authentik's official Proxmox VE integration (OAuth2/OIDC provider, strict redirect URI 'https://<pve-host>:8006', scopes 'email profile entitlements', issuer 'https://authentik.company/application/o/<slug>/', Proxmox realm with Username Claim 'username', Autocreate Users on, optional Groups Claim 'entitlements' + Autocreate Groups) maps authentik application entitlements to Proxmox groups; roles are then granted under Datacenter > Permissions. The doc does not cover API tokens or TFA interplay. <https://raw.githubusercontent.com/goauthentik/authentik/main/website/integrations/hypervisors-orchestrators/proxmox-ve/index.mdx>
- [verified] **Proxmox API tokens and built-in roles:** API tokens are 'USER@REALM!TOKENID=UUID', shown once, optionally expiring, and privilege-separated by default (effective permissions = intersection of user ACLs and token ACLs, so a privsep token needs its own ACL entries). Built-in roles: Administrator, PVEAdmin, PVEVMAdmin, PVEVMUser, PVEDatastoreAdmin, PVEDatastoreUser, PVEAuditor, PVESDNUser, PVEMappingUser, PVEPoolUser, PVETemplateUser, NoAccess. Provisioning-relevant privileges: VM.Allocate, VM.Clone, VM.Config.* (CPU/Memory/Disk/Network/CDROM/Cloudinit/HWType/Options), VM.PowerMgmt, VM.Audit, Datastore.AllocateSpace, Datastore.AllocateTemplate, Datastore.Audit, SDN.Use, Pool.Allocate, Sys.Audit, Sys.Modify, Mapping.Use. <https://pve.proxmox.com/wiki/User_Management>
- [verified] **bpg/proxmox provider version and requirements:** bpg/terraform-provider-proxmox latest release is v0.115.0 (2026-10-02; v0.114.0 on 2026-09-21, v0.112.0 on 2026-09-04). README requirements: targets Proxmox VE 9.x (9.2 tested), 8.x limited/degraded, 7.x unsupported; Terraform >= 1.5 or OpenTofu >= 1.6 (write-only attributes need Terraform 1.11+ / OpenTofu 1.10+); TLS 1.3 enforced by default (min_tls configurable); Go 1.26 to build. Still on Terraform SDKv2 with a migration to the Plugin Framework toward 1.0; 0.x minors may break compatibility. Only v0.109.0 documented a breaking change (agent.wait_for_ip semantics). <https://github.com/bpg/terraform-provider-proxmox/releases>
- [verified] **bpg/proxmox authentication, SSH and least privilege:** bpg supports API token ('user@realm!tokenid=uuid'), username/password, and pre-authenticated ticket auth (env vars PROXMOX_VE_API_TOKEN, PROXMOX_VE_USERNAME/PASSWORD, PROXMOX_VE_AUTH_TICKET, PROXMOX_VE_CSRF_PREVENTION_TOKEN). Docs warn 'Not all Proxmox API operations are supported via API Token' (root-only or feature-flag operations fail even with Administrator tokens). SSH to the node (agent or PEM key; non-root user needs passwordless sudo for /usr/sbin/pvesm apiinfo etc.) is required for uploading snippets via proxmox_virtual_environment_file, importing disks via source_file.path, and container idmap. The documented 'Terraform' role is explicitly 'only an example (and likely too permissive)' and notes the privilege list changed in PVE 9.0. <https://raw.githubusercontent.com/bpg/terraform-provider-proxmox/main/docs/index.md>
- [verified] **Downloading Talos images through the PVE API:** proxmox_virtual_environment_download_file uses the PVE download-url API (no SSH; needs Datastore.AllocateTemplate, Sys.Audit, Sys.Modify), supports content types iso, import and vztmpl, checksum verification, and server-side decompression only for gz, lzo, zst and bz2 - NOT xz. PVE versions before 8.4 reject .raw/.qcow2 names for iso content (use .img). Community OpenTofu setups therefore pull the Talos Image Factory nocloud image as nocloud-amd64.raw.gz (decompression_algorithm = "gz") or .raw.zst instead of the default .raw.xz; the Image Factory API lists .raw.xz, .raw.zst and .raw.gz variants for disk images. <https://raw.githubusercontent.com/bpg/terraform-provider-proxmox/main/docs/resources/virtual_environment_download_file.md>

### Design implications

- CPU/ISA: Node 1 is x86-64-v2 only. Use Proxmox CPU type 'host' for every Talos VM (single host, no live migration; exposes AES-NI/AVX/RDRAND) and never kvm64. Treat any x86-64-v3-only image (GOAMD64=v3 builds, -march=haswell binaries) as unrunnable; add a CI/Renovate note to check this for self-built images and avoid platform components whose upstream images require AVX2.
- No PCIe passthrough design: with chipset-level VT-d assumed absent, do not plan to pass the TX201 NIC, the HD 2500 iGPU or the SATA controller into any VM (no TrueNAS/OPNsense-with-passthrough VM). Both NICs live on the Proxmox host as Linux bridges (vmbr0 on the RTL8111F as the VLAN-aware trunk from OpenWrt; vmbr1 on the TX201 as the point-to-point 2.5 GbE segment to Node 2). The Bluetooth and Wi-Fi USB dongles can still be forwarded to a VM with QEMU USB passthrough, which does not need an IOMMU.
- Memory budget (hard limit 16 GB, no upgrade path on H61): reserve ~1.5 GiB for the PVE host, pin zfs_arc_max explicitly to 1-2 GiB (document the value; the installer default of ~1.6 GiB is acceptable), and allocate at most ~12 GiB to guests. A realistic Talos layout is 1 control plane (4 GiB, 2 vCPU) + 1-2 workers (3-4 GiB each) or a single-node cluster; a 3-control-plane cluster is not affordable and would be logical HA only, not physical HA. Disable ballooning on all Talos VMs and avoid PVE memory overcommit because Talos cannot hot-add memory.
- CPU budget: 4 physical threads total. Over-provision vCPUs modestly (e.g. 2 vCPU control plane + 4 vCPU worker = 6 vCPU on 4 threads) and keep Hubble, OpenBao and the observability stack sized minimally; measure before adding components (CLAUDE.md section 23).
- Storage decision for the single 256 GB SATA SSD (3 Gb/s port): recommended default is ZFS single-disk rpool installed with compression=on, ARC capped, autotrim enabled, and a documented plan to add a second SSD later via zpool attach + proxmox-boot-tool (three free SATA ports). Record the trade-off in an ADR: ZFS gives checksums, snapshots, send/receive replication to Node 2/PBS and consistent backups, at the cost of higher write amplification on a consumer SSD without PLP; monitor SMART wear (smartctl exporter) from day one. If the user prefers minimal wear and simplicity, ext4 + LVM-thin is the acceptable alternative with the same snapshot support but without checksums/replication.
- Firmware preparation checklist before any install (must be done at the console, document it as the only manual step): update the board BIOS to the latest F-version for its revision, set SATA mode to AHCI (H61 firmware defaults may be IDE), enable Intel Virtualization Technology, decide UEFI vs legacy boot (prefer UEFI if the AMI firmware boots the PVE 9.2 ISO reliably; legacy BIOS + GRUB on ZFS is fully supported otherwise), disable unused onboard audio/serial, and set 'power on after AC loss' so the host recovers without a keyboard.
- Proxmox version pin: install Proxmox VE 9.2 (Debian 13.5, kernel 7.0) from the official ISO and track the 9.x line; do not use community helper scripts. Because Proxmox Bugzilla 7237 (Realtek 100 Mbps on kernel 6.17) is unresolved in the sources found, validate link speed with 'ethtool' on both NICs right after install; if the 2.5 GbE link to Node 2 negotiates 100 Mbps, pin the 6.14 opt-in kernel (proxmox-boot-tool kernel pin) rather than installing the r8125 DKMS, and record the pin as technical debt with a removal task.
- Network drivers: keep the in-tree r8169 for both NICs, never install realtek-r8125-dkms (it taints upgrades and breaks on kernel bumps). The 2.5 GbE link is a dedicated back-to-back segment (no switch): model it as its own small subnet (/30 or /31) used only for Proxmox-to-Node 2 traffic (PBS backups, ZFS send, Talos worker on Node 2 if approved), with firewall rules so it is not a bypass of the VLAN policy matrix.
- OpenTofu provider stack and pins: OpenTofu 1.13.x, bpg/proxmox ~> 0.115 (pin exact minor; 0.x has no compatibility guarantee, so Renovate PRs must run tofu plan in CI), siderolabs/talos ~> 0.12 (use the new talos_machine + talos_cluster resources, ephemeral talos_cluster_kubeconfig/talos_client_configuration so kubeconfig/talosconfig never land in state), and SOPS/age-encrypted tfvars. Do not use Telmate (RC-only, PVE 9 permission breakage).
- Proxmox IAM for automation: create terraform@pve and kubernetes-csi@pve with privilege-separated API tokens that have expiry dates, each bound to a custom role built from the PVE 9 privilege list (VM.Allocate, VM.Clone, VM.Config.*, VM.PowerMgmt, VM.Audit, VM.GuestAgent.Audit, Datastore.AllocateSpace, Datastore.AllocateTemplate, Datastore.Audit, SDN.Use, Pool.Allocate, Sys.Audit, Sys.Modify for the OpenTofu role; the documented five-privilege CSI role for the CSI token). Never grant Administrator to a token; never reference VM.Monitor. Keep root@pam with TOTP/WebAuthn as break-glass only; document rotation (token expiry) in SECURITY.md.
- Avoid SSH dependence in IaC: design the Talos pipeline so the bpg provider needs API access only - download the Image Factory nocloud image with proxmox_virtual_environment_download_file (choose nocloud-amd64.raw.gz or .raw.zst because PVE cannot decompress xz; verify the exact URL exists for the pinned Talos version), attach it as the VM's import/boot disk, use PVE cloud-init only for static IP/hostname via the initialization block, and apply the full machine config over the Talos API with the talos provider. This removes the need for cicustom snippets (SSH + root shell), keeps the token-only auth model, and makes the DR rebuild path fully API-driven.
- Talos VM template definition (to encode in the OpenTofu module and test once): OVMF + q35 + EFI disk (pre-enrolled keys off unless Secure Boot image is used), CPU 'host', 2-4 vCPU, memory fixed with balloon=0, scsihw virtio-scsi (test the Talos docs' warning against 'virtio-scsi-single'; if single+iothread works on PVE 9.2 with Talos 1.14 use it and document the deviation), scsi0 with discard=on, ssd=1, cache=none, a 32-60 GiB system disk, virtio NIC with multiqueue=vCPUs and VLAN tag 50, serial0 console, qemu-guest-agent extension baked into the schematic (siderolabs/qemu-guest-agent + siderolabs/intel-ucode) so the PVE agent option can be enabled for clean shutdowns and IP reporting. Pin the schematic ID and Talos version in Git.
- Kubernetes storage: with a single physical disk, use the Proxmox CSI plugin (zfspool or lvm-thin backend) for PersistentVolumes instead of Longhorn/Rook, because it adds no replication overhead on a host that has no redundancy anyway; application-level durability comes from CloudNativePG backups and Restic/Kopia to Node 2 and off-site. Document that PV data on Node 1 is a single copy until the second SSD/mirror exists.
- Identity: integrate Proxmox with Authentik via the OIDC realm (issuer https://<authentik>/application/o/<slug>/, username-claim 'username', groups-claim 'entitlements', autocreate users/groups, PKCE) and bind Proxmox groups to roles with ACLs; this covers human web logins only. Because Authentik itself runs inside the cluster on this host, there is a circular dependency on first boot and during DR - keep a local pam/pve admin with MFA as break-glass and list it in DISASTER-RECOVERY.md.
- Power, UPS and consistency: estimated 25-40 W idle (~1 kWh/day) is cheap to run 24/7, but the SSD has no power-loss protection and ZFS/cloud-native databases dislike sudden power cuts; a small UPS with NUT on the PVE host (clean shutdown of Talos VMs via guest agent) is a strongly recommended, inexpensive addition to protect against the CGNAT/ISP-area power environment. Also plan hardware obsolescence: the CPU is out of Intel servicing (no microcode fixes since 2019), DDR3 is capped at 16 GB, and SATA is 3 Gb/s - record this as the main driver for any future hardware refresh and keep everything reproducible so a move to new hardware is an OpenTofu re-apply.
- Talos lifecycle: Talos supports only the two latest minors (1.13 and 1.14 today; 1.15 due around late December 2026) with Kubernetes 1.33-1.37 on 1.14, so Renovate must track Talos minor releases and the pipeline must handle upgrades via talos_machine (image bump) and talos_cluster (kubernetes_version bump) rather than ad-hoc talosctl commands; keep Kubernetes within the supported skew of the Talos version.

## Network hardware, OpenWrt and remote access

The network hardware is adequate for the VLAN design, with one important asymmetry: the D-Link M30 (OpenWrt target mediatek/filogic, MT7981 dual-A53 @1.3 GHz, 512 MB RAM, 128 MB NAND dual-UBI, MT7531 switch) is a modern DSA router whose four LAN ports can run a VLAN-aware bridge with 802.1Q trunks, while the two Xiaomi Mi Router 4A Gigabit APs (MT7621, 128 MB RAM, 16 MB flash) sit exactly at OpenWrt's documented 16/128 floor and must stay pure dumb APs (multi-SSID-to-VLAN via bridge-vlan, no tailscale or other large packages). OpenWrt 25.12 is the current stable series (25.12.0 on 5 Mar 2026, 25.12.5 on 1 Jul 2026, apk replaced opkg, attended sysupgrade preinstalled); 24.10 lost security support after September 2026 and no 26.x branch exists yet, so all three devices should be pinned to 25.12.x. Both the M30 (since 23.05.4) and the Xiaomi v1 and v2 profiles ship in 25.12.5 (verified from the release download tree). Inter-VLAN routing on the M30 is CPU-routed through a single 2.5G CPU port: expect roughly gigabit line rate (~940 Mbps) per flow with software flow offload, 2.5 Gbps aggregate ceiling, and treat hardware offload/WED as an opt-in experiment because of documented latency and binding caveats. Because Node 1 has only one 1 GbE uplink to the router, any VM-to-VM traffic between different VLANs on Node 1 hairpins through that single cable, which argues for keeping east-west traffic inside VLAN 50 and using the direct 2.5 GbE Node1-Node2 link (own subnet, no router) for backup traffic. For declarative management the clear choice is the Ansible collection community.openwrt (Galaxy, v1.8.0 on 2026-09-22, ucode-based uci/apk/service modules, tested on 25.12), combined with Git-tracked `uci export` snapshots and optionally ImageBuilder + uci-defaults for reproducible images; the gekmihesg role was archived in Feb 2026 and the only Terraform provider has been dormant since April 2023. OpenWrt dnsmasq supports zone forwarding (`list server '/zone/ip'`, requiring `rebind_domain` for RFC1918 answers), per-VLAN DHCP pools with static leases, and prometheus-node-exporter-lua (2026.06.05, 6 KB) is in the 25.12 feed with wifi/hostapd/nft collectors. Under CGNAT with no IPv6 and no inbound ports, Tailscale (free Personal plan, 6 users, subnet routers) is the lowest-friction private-access path, Cloudflare Tunnel plus Access (free under 50 users) is the right tool for published HTTPS apps and identity-gated SSH/RDP, Cloudflare Mesh (GA Apr 2026) covers bidirectional site-to-site if ever needed, and a WireGuard VPS ($4/month DigitalOcean or Oracle Always Free with idle-reclamation risk) or headscale (v0.29.4, needs a public VPS anyway) are fallbacks rather than first choices.

### Design implications

- Pin all three OpenWrt devices (M30 + both Xiaomi APs) to the 25.12.x series (currently 25.12.5); 24.10 is past its September 2026 security cut-off. Because 25.12 uses apk, every automation path (Ansible community.openwrt apk module, ImageBuilder PACKAGES, docs) must assume apk, not opkg.
- Before touching the APs, determine their current OpenWrt version and whether they are v1 or v2: if they still run 19.07 or older (swconfig), the upgrade to a DSA release requires 'sysupgrade -n -F' (config wipe) and a re-provision from Git; v1 vs v2 selects a different image profile and the wrong one will brick the 5 GHz radio or fail to boot.
- The M30 can implement the VLAN plan on its four MT7531 LAN ports via a VLAN-aware br-lan with bridge-vlan sections (LAN1 -> Node 1 as 802.1Q trunk carrying 10/40/50 (+20 if needed); LAN2 -> Node 2 as access VLAN 20 or trunk; LAN3/LAN4 -> APs as trunks carrying 20/60/70 tagged plus management VLAN 10 untagged/PVID). The WAN port is a separate GMAC and should stay out of the bridge. Keep WAN/LAN zones default-deny with explicit 'config forwarding' per allowed VLAN pair and 'config rule' exceptions for DHCP/DNS/NTP to the router, tracked in Git.
- Size expectations: inter-VLAN flows top out at roughly gigabit per flow with software flow offloading, with a 2.5 Gbps aggregate ceiling at the CPU port; enable flow_offloading=1 by default, leave flow_offloading_hw=0 until measured (documented latency regressions on MT7981), and only enable WED if Wi-Fi throughput becomes a problem. Record this in the architecture doc instead of advertising '2.5G routing'.
- Node 1's single 1 GbE uplink means any traffic between two VLANs that both live on Node 1 (e.g. a management VM in VLAN 10 and Talos in VLAN 50) hairpins through the M30 over the same cable. Design to keep heavy east-west traffic inside VLAN 50 (Talos nodes, CNPG, storage, Argo CD) and use the direct 2.5 GbE Node1<->Node2 link as a dedicated point-to-point subnet (not routed by the M30) for PBS/restic backup traffic and iperf validation.
- Treat the Xiaomi 4A Gigabit units strictly as dumb APs: 16 MB flash / 128 MB RAM allows OpenWrt 25.12 (7.5-7.9 MB image) plus tiny packages (node-exporter-lua collectors are 1-6 KB) but not tailscale (9.7 MB apk) or similar. Configure multi-SSID-to-VLAN with bridge-vlan on br-lan, uplink port tagged, wifi-iface 'option network' per VLAN, DHCP disabled, management IP in VLAN 10 only.
- Adopt Ansible with the community.openwrt collection (>=1.8.0, uci + apk + service modules, ucode-based so no Python on the device) as the single declarative management path for the router and APs, driven from WSL now and GitHub Actions later; store full 'uci export' snapshots in Git for drift detection and add a CI job that diffs live export vs Git. Do not build on the archived gekmihesg role or the 2023-dormant joneshf Terraform provider. Bootstrap requirement: a homelab-specific SSH key installed in dropbear on all three devices (currently absent).
- For reproducibility/DR, add an ImageBuilder pipeline (profile dlink_aquila-pro-ai-m30-a1 and the two Xiaomi profiles) that bakes PACKAGES and files/etc/uci-defaults from Git, so a dead router can be rebuilt from a recovery image without manual LuCI steps; keep the M30 recovery .bin for the exact installed release in the backup set (recovery flow differs across 24.10.2/24.10.3+, needs Chromium).
- DNS design on the M30: dnsmasq forwards the cluster zone (e.g. k8s.<domain>) to a CoreDNS/external-dns resolver in VLAN 50 via 'list server' and MUST include 'list rebind_domain' for that zone, or RFC1918 answers are dropped; per-VLAN 'config dhcp' pools with 'config host' static leases for Node 1, Node 2 UE302C link, APs and the ESP32 (move it to VLAN 60) all live in Git.
- Monitoring: install prometheus-node-exporter-lua with -openwrt, -wifi, -wifi_stations, -hostapd_stations, -netstat, -nft-counters, -thermal collectors on the M30 and APs; scrape from Prometheus in VLAN 50 to VLAN 10 on the exporter port with an explicitly documented firewall exception (Kubernetes -> Management is denied by default).
- Remote access under CGNAT: make Tailscale (free Personal plan, up to 6 users, subnet routers + exit nodes) the primary admin path, running tailscaled as a subnet router in a small Proxmox VM/LXC on Node 1 advertising VLAN 10 (never on Talos nodes, never on the APs); optionally also on the M30 (fits in 128 MB NAND) as an independent second path. Verify first that the ISP's CGNAT does not place the router WAN in 100.64.0.0/10 (Tailscale's own range). Expect DERP-relayed throughput when hole-punching fails.
- Use Cloudflare Tunnel + Access (free under 50 users) for published HTTPS apps and for identity/MFA-gated SSH or RDP to Node 2 (browser or client-side cloudflared), keeping Proxmox, Talos API, OpenBao and the OpenWrt UI off the public Tunnel entirely. Do not proxy bulk media through the public Tunnel (CDN terms); private-network routes via WARP are exempt and can be an alternative to Tailscale if the user prefers a single Cloudflare identity plane.
- Defer headscale (needs a public VPS plus operations, no benefit on the free Tailscale tier for one admin) and WireGuard-on-VPS to documented fallbacks; if a VPS is wanted later, DigitalOcean $4/month (Bangalore) or Oracle Always Free (with the 7-day idle reclamation risk) are the verified price points. Record this as an ADR with the CGNAT constraint as the driver.
- Node 2 (Windows 11 + Hyper-V): the Tailscale Windows client and Cloudflare One client coexist; a PBS or burst-worker VM under Hyper-V can join the tailnet directly, so Node 2 does not need any router port-forwarding and can reach VLAN 10/50 via the subnet router even when away from home.

## Talos, Kubernetes, Cilium, Gateway API and Argo CD

As of 2026-10-05 the platform stack is mature and well-pinned: Talos 1.14.2 (Kubernetes 1.37.1, Linux 6.18, etcd 3.7, Image-Factory-only installer images), Cilium 1.20.2 (Gateway API v1.6.1 support, GA LB-IPAM, beta L2 announcements, brand-new but buggy ExternalAuth), Gateway API v1.6.2 (TCP/UDPRoute GA; ListenerSet and GEP-1494 ExternalAuth still Experimental), Argo CD 3.5.3, cert-manager 1.21.2, external-dns 0.23.0, ESO 2.11, OpenBao 2.7.1, CNPG 1.30.1, Loki 3.7.8, Alloy 1.20.1, Authentik 2026.8.3 (no Redis since 2025.10). Talos minimums are 2 GiB/2 vCPU for a control plane and 1 GiB/1 vCPU for a worker (4/2 GiB recommended), amd64 needs only x86-64-v2, which the i5-3570 satisfies; its real idle overhead is nearer 0.8-1.5 GiB on a control plane, so a 3-control-plane cluster would burn roughly a quarter of the 16 GB host for purely logical HA that cannot survive the single physical host anyway. Talos upgrades cordon, drain and reboot each node (A/B rollback, no minor-version skipping, control-plane upgrades serialized and refused if they would break etcd quorum); with one control plane that means a few minutes of API unavailability while workers keep running, and on a single-node cluster it means a full outage, which must be documented honestly. etcd backup is first-class (talosctl etcd snapshot / bootstrap --recover-from) and is the DR anchor alongside Proxmox VM backups. For ingress with Authentik forward-auth, Traefik 3.7.13 is the lowest-footprint mature choice (HTTPRoute ExtensionRef to a ForwardAuth Middleware, v1.6 conformance report, official authentik docs), Envoy Gateway 1.9.2 is the richest (native extAuth and OIDC SecurityPolicy, v1.6 conformance) at ~300-400 MiB, and Cilium's own Gateway ExternalAuth should not be the security boundary until the open 1.20.x regressions are fixed. Argo CD upstream explicitly recommends destination-cluster secret management (ESO) over decrypting SOPS in the repo-server, so "ESO + OpenBao at runtime, SOPS/age only for bootstrap secrets handled outside Argo CD" is the endorsed pattern; KSOPS 4.5.1 and helm-secrets 4.7.8 remain maintained fallbacks. Behind CGNAT the only viable public path is Cloudflare Tunnel (outbound-only, no public IP needed), with external-dns managing Cloudflare records and the Codeberg-maintained k8s_gateway (v1.9.0) or a static dnsmasq wildcard for split-horizon LAN DNS, and cert-manager pointed at public recursive resolvers for its DNS-01 self-check. Idle RAM for the full requested platform (Cilium, Argo CD, kube-prometheus-stack, Loki/Alloy, Authentik+Postgres, cert-manager/ESO/OpenBao/external-dns, gateway, CNPG, VolSync, Proxmox CSI, cloudflared) is estimated at 5-8 GiB before any application, plus ~2 GiB of Talos/Kubernetes node overhead across three VMs, which leaves only 3-6 GiB for applications on this host and argues for phased deployment, conservative scrape intervals, Loki monolithic mode and skipping Hubble UI by default. Node 2 can host a Hyper-V Talos worker (official guide; Secure Boot must be off) but only for stateless, taint-isolated burst work because the laptop reboots and Proxmox-CSI local volumes are pinned to Node 1.

### Design implications

- Cluster shape on the 16 GB host: a 3-control-plane Talos cluster costs ~3-4.5 GiB of pure control-plane overhead (3 x >=2 GiB VMs) and buys only logical HA (etcd quorum against a VM crash, zero-API-downtime upgrades) because all VMs die with the single Proxmox host. Recommended default: 1 control plane (3 GiB, allowSchedulingOnControlPlanes: false) + 2 workers (~5 GiB each), leaving ~1.5 GiB for Proxmox itself, and document that a Talos OS upgrade of the control plane means a few minutes of Kubernetes API unavailability while workloads keep running on the workers. A single-node cluster (1 VM, 12-13 GiB) is the fallback if memory is too tight; its upgrades are full outages (node cordons, drains and reboots). Never describe either as physical HA.
- Memory budget reality: the requested platform idles at an estimated 5-8 GiB (Cilium 0.6-1.2, Argo CD 0.6-1, kube-prometheus-stack 1-1.8, Loki+Alloy 0.6-1.3, Authentik+PostgreSQL 0.8-1.4, cert-manager/ESO/OpenBao/external-dns 0.3-0.7, gateway 0.1-0.4, CNPG 0.2-0.4) plus ~2 GiB of Talos/Kubernetes node overhead across three VMs, so only ~3-6 GiB remain for applications. Consequences: deploy strictly in phases with measured `kubectl top` after each; set Prometheus to 30-60 s scrape and 7-15 d retention; run Loki in monolithic mode (well under its ~20 GB/day guidance); run Alloy as a DaemonSet instead of Promtail (removed in Loki 3.7.3); enable hubble-relay for CLI debugging but leave Hubble UI off by default; postpone OpenBao until ESO has a consumer and consider Authentik as the single largest non-observability tenant.
- CPU and virtualization: the i5-3570 satisfies x86-64-v2 (Talos boots) and has VT-x/EPT, VT-d and AES-NI, so Proxmox's default x86-64-v2-AES CPU type or host passthrough both work; no AVX2 means avoid any component that ships x86-64-v3-only binaries. With only 4 cores/4 threads, size VMs as 2 vCPU control plane + 2-3 vCPU per worker with overcommit, and keep Hubble/L7 policy CPU overhead in mind.
- Disk layout on the single 256 GB SSD: Proxmox ~20 GB (prefer LVM-thin over ZFS to avoid ARC consuming RAM [assumption]); Talos control plane 20-32 GiB and workers 40-60 GiB system disks (EPHEMERAL holds images and must not fill); application PVs via Proxmox CSI (lvm-thin, thin-provisioned) pinned to Node 1 - which is fine for a single Proxmox node but means a Node 2 worker can never mount them. Keep all backups off this disk (Proxmox Backup Server or restic repo on Node 2's 2 TB SSD plus the off-site copy).
- Talos operations contract: pin an Image Factory schematic (siderolabs/qemu-guest-agent; add intel-ucode; iscsi-tools only if an iSCSI CSI is adopted later) and use factory.talos.dev/metal-installer/<schematic>:<version> everywhere, because ghcr.io/siderolabs/installer no longer exists for 1.14. Renovate must step Talos one minor at a time (latest patch of each intermediate minor) and Kubernetes one minor at a time; start new clusters on multi-document config with SecurityProfileConfig workloadIsolation: true (the 1.14 default) and note that it breaks only the in-tree iSCSI plugin, not Proxmox CSI. Schedule `talosctl etcd snapshot` (e.g., daily via a `just` task or CronJob with talosctl credentials) and copy snapshots off-host; this plus Proxmox VM backups is the documented DR anchor (restore = rebuild VMs with OpenTofu, `talosctl bootstrap --recover-from`).
- Cilium configuration for Talos: delete the KubeFlannelCNIConfig document, disable kube-proxy (KubeProxyConfig enabled: false), install Cilium with kubeProxyReplacement=true, k8sServiceHost=localhost, k8sServicePort=7445 (KubePrism), ipam.mode=kubernetes, cgroup.autoMount.enabled=false, cgroup.hostRoot=/sys/fs/cgroup, the documented capability list, and enable the DNS/L7 proxy so toFQDNs egress allow-lists work. Deliver Cilium as the Talos inline manifest or via the bootstrap step before Argo CD, then hand ownership to Argo CD.
- LAN exposure without BGP: use Cilium LB-IPAM (GA) with a small pool inside VLAN 50 plus L2 Announcements (beta; single announcing node per IP, no externalTrafficPolicy: Local) for the Gateway's LoadBalancer IP. Skip BGP: the OpenWrt M30 would need bird2/frr and it adds no value on a single-host cluster [unverified]. Protect node ports with Talos' nftables ingress firewall (NetworkDefaultActionConfig block + rules for 50000/6443/10250/2379-2380 from VLAN 10 and the node CIDR) rather than Cilium host firewall initially, because of the documented lockout risk.
- Public exposure under CGNAT: cloudflared (2 replicas, tunnel token in an ESO-managed Secret, Cloudflare's official Deployment pattern or the community-charts/lexfrei chart) is the only path; no port forwarding or IPv6 is possible. Route public hostnames through the tunnel to the in-cluster Gateway; have external-dns (Cloudflare provider, scoped token Zone Read + DNS Edit, cloudflare-proxied=true) manage CNAMEs to the tunnel; keep Proxmox, Talos API, Kubernetes API, Argo CD and OpenBao LAN/VPN-only (optionally behind Cloudflare Access for the few admin UIs that must be remote).
- Split-horizon DNS: run k8s_gateway (Codeberg fork v1.9.0, chart 3.7.4) as a tiny CoreDNS with its own LB IP and have OpenWrt dnsmasq forward the internal zone to it, or, simpler for phase 7, add a static dnsmasq wildcard address for the lab zone pointing at the Gateway IP. Set cert-manager's --dns01-recursive-nameservers=1.1.1.1:53,8.8.8.8:53 and --dns01-recursive-nameservers-only so the DNS-01 self-check is not fooled by internal answers; issue one wildcard certificate per zone via Cloudflare DNS-01 (API token with Zone:Read + DNS:Edit, scoped to the one zone).
- Gateway choice with Authentik forward-auth: (a) Traefik v3.7.13 - smallest footprint, v1.6 conformance report, HTTPRoute ExtensionRef -> ForwardAuth Middleware pointing at the authentik outpost (/outpost.goauthentik.io/auth/traefik), but TCPRoute needs experimental CRDs; (b) Envoy Gateway v1.9.2 - ~300-400 MiB, v1.6 conformance, native SecurityPolicy extAuth (/outpost.goauthentik.io/auth/envoy) and native OIDC at the edge; (c) Cilium Gateway - no extra pods, but its ExternalAuth is new in 1.20 with an OPEN regression (#49132) on >=1.20.2 and GEP-1494 is still Experimental, so do not make it the auth boundary before Cilium 1.21. Recommendation for 16 GB: Traefik now; revisit Envoy Gateway if edge OIDC or GA TCP/UDP routes become requirements; keep Cilium's gatewayAPI.enabled=false to avoid running two Gateway controllers.
- GitOps and secrets: follow Argo CD's own guidance - no SOPS decryption inside the repo-server. Runtime secrets flow Git (ExternalSecret CRs) -> ESO (Vault provider) -> OpenBao (single Raft node, static seal with the 32-byte key kept SOPS/age-encrypted in Git and in Bitwarden). SOPS/age is used only for bootstrap material consumed by `just`/OpenTofu/talosctl outside Argo CD (Talos secrets bundle, Cilium/Argo bootstrap values, OpenBao seal key, Cloudflare tokens until OpenBao exists). KSOPS 4.5.1 remains a documented fallback if a secret truly cannot wait for OpenBao. Structure Argo CD as ApplicationSets (Git directory generator per layer) with sync waves ordering CRDs/Cilium -> cert-manager -> ESO/OpenBao -> gateway -> observability -> apps; use multi-source Applications for upstream Helm charts with values from Git; pin every chart version; expect ~0.6-1 GiB for Argo CD and set --parallelismlimit on repo-server.
- Node 2 as burst worker: feasible via the official Hyper-V guide (Gen2, Secure Boot OFF, external vSwitch on the direct 2.5GbE link) but it is a Windows laptop that reboots and sleeps, so: never run etcd/control plane there, taint it (NoSchedule) and only tolerate stateless burst workloads, keep Cilium in native routing on the shared L2 (the ExternalAuth cross-node bug needs WireGuard+tunnel mode), and accept that Proxmox-CSI local volumes on Node 1 cannot follow pods there. Memory share of Node 2 (of 15.4 GiB with WSL2 already allotted 8 GiB) must be decided by the user.
- Version pinning baseline for Phase 1 (Renovate targets): Talos 1.14.2 / Kubernetes 1.37.1, Cilium 1.20.2, Gateway API CRDs 1.6.2 standard channel, Traefik 3.7.13 (or Envoy Gateway 1.9.2), Argo CD 3.5.3, cert-manager 1.21.2, external-dns 0.23.0, ESO 2.11, OpenBao 2.7.1, Authentik 2026.8.3, kube-prometheus-stack 91.9.0, Loki 3.7.8 (grafana-community chart), Alloy 1.20.1, CNPG 1.30.1, VolSync 0.16.0, Proxmox CSI 0.20.0, metrics-server 0.9.0 (+ kubelet-serving-cert-approver), k8s_gateway 1.9.0, cloudflared 2026.9.x.

## Secrets and identity

Secrets and identity for this homelab resolve to a three-layer design: SOPS+age for everything that must exist before the cluster does (Talos secrets bundle, OpenTofu tfvars, Ansible vars, the handful of Argo CD bootstrap Secrets), OpenBao KV v2 as the runtime secret authority, and External Secrets Operator (ESO) pulling from OpenBao into Kubernetes, with Authentik as the single OIDC identity provider. All versions were checked against primary sources on 2026-10-05: OpenBao 2.7.1 (chart 0.30.2), ESO 2.11.0, SOPS 3.13.3, age 1.3.2, Authentik 2026.8.3, and the comparison set Keycloak 26.8.0, Authelia 4.39.28, Pocket ID 2.18.0, Zitadel 4.19.4. The most consequential finding for a frequently-rebooted single host is that OpenBao has had a first-class static-key auto-unseal since 2.4.0 (`seal "static"` reading a 32-byte key from file:// or env://), which removes the need for manual Shamir unsealing or a second always-on OpenBao for transit unseal, at the documented cost of trusting whatever store holds that key (here a Kubernetes Secret created at bootstrap from a SOPS-encrypted manifest, with the key also in Bitwarden). OpenBao 2.7 also moved cloud-KMS seals into external plugins and deleted the file storage backend, so the single-node choice is between PebbleDB (chart standalone default) and single-replica integrated Raft; Raft is preferable because `bao operator raft snapshot` is the backup/DR primitive and it scales to 3 voters later without a storage migration. ESO now carries a separate OpenBao provider, but it is Alpha (Kubernetes auth landed only in v2.10, Aug 2026), so the stable Vault provider should be pointed at OpenBao instead; ESO supports only its latest minor, forcing Renovate-driven upgrades roughly every three weeks. Authentik removed Redis in 2025.10 (server with embedded proxy outpost + worker + PostgreSQL 14-18 only), rewrote its server entrypoint and proxy outpost in Rust and became OpenID Certified in 2026.8, and the Helm chart ships no Redis and disables the bundled PostgreSQL by default, so CloudNativePG is the intended backing store; its official floor is 2 cores/2 GB, which is the single largest identity cost on a 16 GB host. OIDC coverage is broad: Proxmox VE (realm since 7.0, groups-claim since 8.4), PBS (since 2.0), Argo CD (direct oidc.config, Dex can be disabled), Grafana OSS (generic_oauth), OpenBao (jwt/oidc auth with CLI callback on :8250), and Cloudflare Access (generic OIDC with a documented Authentik recipe); Hubble UI and OpenWrt LuCI have no OIDC and need Traefik forwardAuth (Gateway API ExtensionRef -> Middleware works in Traefik v3.7) or must remain local-account exceptions. Because the ISP uses CGNAT, Cloudflare Tunnel (outbound-only) is the only viable inbound path; the Zero Trust free plan caps at 50 seats and Access with Authentik as IdP is appropriate for admin/semi-private apps, while Cloudflare's CDN terms still discourage streaming media through it. Among alternatives, Pocket ID (~50 MB, passkey-only, OIDC-certified) is the only one that would materially cut RAM, but it lacks forward-auth, LDAP/RADIUS outposts and SAML, so Authentik remains the right default with Pocket ID recorded as the lean fallback in the ADR.

### Design implications

- Secret layering: SOPS+age (bootstrap, Git) -> OpenBao KV v2 (runtime authority) -> ESO ClusterSecretStore with Kubernetes auth (delivery). Only the pre-cluster artefacts live in SOPS: Talos secrets.yaml, OpenTofu tfvars, Ansible host/group vars, and the 3-4 Argo CD bootstrap Secrets (OpenBao static unseal key, cloudflared tunnel token, Argo CD repo credentials). Everything else is created in OpenBao and synced by ESO; nothing is ever committed in plaintext.
- OpenBao deployment on the 16 GB host: one pod, integrated Raft with server.ha.enabled=true, server.ha.raft.enabled=true, server.ha.replicas=1 (document explicitly as logical-only, no HA), ui.enabled=true for OIDC login, requests ~128Mi/limit 256Mi, 2-5 Gi PVC on SSD. Choose Raft over the chart's PebbleDB standalone because `bao operator raft snapshot` is the backup/DR primitive and the path to 3 voters later needs no storage migration. Pin >= 2.7.1 because of the Kubernetes SA JWT validation fix; note cloud-KMS seals are plugins now (irrelevant here).
- Unseal strategy for a host that will lose power/reboot: use `seal "static"` with current_key = file:///openbao/unseal/key mounted from a Kubernetes Secret in the openbao namespace, RBAC-restricted, created at bootstrap from a SOPS-encrypted manifest. Record in the ADR that whoever can read that Secret (or etcd) can unseal; store the static key and the recovery keys in Bitwarden (user already runs it) and keep a printed copy. Do NOT depend on a transit unsealer on Node 2 (laptop availability) nor on bakito/vault-unsealer (redundant now). Create a follow-up task to evaluate a hardware-rooted key (TPM/YubiKey) once the base platform is stable.
- ESO: deploy chart 2.11.x into external-secrets with controller+webhook+cert-controller (set explicit requests ~ 3 x 32-64Mi). Use the Stable `vault` provider pointed at OpenBao (version v2, path kv, Kubernetes auth mountPath kubernetes, caProvider from the cert-manager internal CA), not the Alpha `openbao` provider; revisit when it reaches Beta. Because ESO supports only its latest minor, Renovate must track ESO and the cluster should expect roughly a three-week upgrade cadence; group ESO CRD and chart bumps together.
- Use PushSecret for secrets generated inside the cluster (CloudNativePG app/superuser credentials, auto-generated admin passwords) so OpenBao holds the authoritative copy and DR can restore applications from an OpenBao raft snapshot; use the Password generator for first-run credentials instead of hand-written values.
- age key custody: generate one operator identity on Node 2 (keep a single copy, either WSL ~/.config/sops/age/keys.txt or Windows %AppData%\sops\age\keys.txt, and point SOPS_AGE_KEY_FILE at it from the other side), plus one offline recovery identity whose private key lives only in Bitwarden + paper; every creation_rule lists both recipients so loss of the laptop is survivable. Never place an age private key on Node 1 or in the cluster. Key rotation procedure = edit .sops.yaml, `sops updatekeys -y` over the tree in one PR; data-key rotation = `sops rotate -i`. Document a yearly rotation and an immediate rotation on device loss.
- Avoid giving CI an age key: run only validation (sops --decrypt is not needed for yamllint/kubeconform/tofu validate if encrypted files are excluded or use a dummy backend). If a future workflow truly needs decryption, create a third, CI-only recipient held as a GitHub secret with minimal path_regex scope.
- OpenTofu secrets: keep provider credentials out of tfvars by using `sops exec-env` (or sops_file data source) and turn on OpenTofu state encryption from day one (PBKDF2 passphrase delivered via environment from SOPS, later the OpenBao transit key provider once OpenBao exists). Prefer ephemeral resources / write-only attributes (OpenTofu >= 1.11) for cloud-init passwords and API tokens so they never land in state; pin opentofu 1.13.x and carlpett/sops 1.4.x in Renovate.
- Talos: commit talos/secrets.sops.yaml (age-encrypted output of `talosctl gen secrets`) and generate machine configs with `--with-secrets` in a wrapper (talhelper is an acceptable helper but adds a tool; decide in the Talos ADR). Treat the talosconfig admin client cert as a secret with the same custody rules.
- Identity: keep Authentik as the IdP (needed for forward-auth, LDAP/RADIUS outposts, SAML, user self-service) but budget it honestly: server + worker ~1 GiB, 1 replica each, no Redis (2025.10+), backed by a CloudNativePG cluster with 1 instance (no HA claim) sized for Authentik's ~50% higher connection count (max_connections >= 100; consider the CNPG pooler in transaction mode, supported since 2026.8). Record Pocket ID (~50 MB, passkey-only) as the lean fallback in ADR-0001 if RAM becomes the binding constraint.
- Authentik 2026.8 breaking change: set AUTHENTIK_LISTEN__TRUSTED_PROXY_CIDRS explicitly to the Cilium pod CIDR and the Traefik service range (defaults cover RFC1918 only), set the Base URL system setting now (mandatory in 2026.11), and make Traefik trust Cloudflare's forwarded headers only on the tunnel-facing entrypoint so Authentik sees the real client IP for brute-force policies.
- OIDC rollout order (each with a local break-glass account + MFA documented in a runbook because Authentik runs inside the cluster it protects): 1) Argo CD direct oidc.config with dex.enabled=false (saves a pod), groups -> role:admin/readonly; 2) Grafana generic_oauth with entitlement-based role mapping; 3) OpenBao jwt/oidc auth (CLI callback :8250 and UI callback) with groups -> policies, then revoke the root token; 4) Proxmox VE 9.x openid realm with groups-claim/autocreate mapped to a pve-admins group; 5) PBS 4.x openid realm; 6) Hubble UI and any auth-less dashboards behind a Traefik forwardAuth Middleware referenced from HTTPRoute via ExtensionRef (Traefik v3.7+, same namespace) using Authentik's embedded outpost; 7) OpenWrt LuCI stays local root + SSH key only and is listed as a documented exception.
- Cloudflare: CGNAT and no IPv6 mean Cloudflare Tunnel is the only inbound path, so the DMZ design is cloudflared (in-cluster, 2 replicas for logical HA) -> Traefik Gateway -> apps. Put Cloudflare Access (free, 50 seats) with Authentik as OIDC IdP in front of every admin or household-only app exposed through the tunnel (defence in depth: Access JWT at the edge, Authentik session at the app); never publish Proxmox, PBS, OpenBao, the Talos/Kubernetes API, Argo CD or Hubble through the tunnel at all. Truly public apps either get an Access Bypass policy or no Access app, with authentication enforced by Authentik. Do not stream self-hosted media through the tunnel (CDN terms); remote media access needs a separate answer (open question).
- Node 2 role for secrets/identity: it is the operator workstation and key custodian (age keys, Bitwarden, talosconfig), not a trust anchor for the cluster; do not make OpenBao unsealing or Authentik availability depend on the laptop. If a PBS VM runs on Node 2's 2 TB SSD, enable its openid realm against Authentik but keep root@pam with TOTP as break-glass since PBS must be reachable when the cluster is down.
- Backup/DR for the secret system = three independent copies: (a) Git with SOPS files + age recovery key in Bitwarden/paper, (b) nightly `bao operator raft snapshot` pushed off-site via restic (encrypted), (c) CloudNativePG Barman backups of the Authentik database. Restore drill order in the DR runbook: age key -> SOPS bootstrap secrets -> OpenBao raft restore + static unseal -> ESO reconciles -> Authentik DB restore -> OIDC clients come back with the same client IDs/secrets (keep them in OpenBao, not only in Authentik).
- Resource budget line items for the platform table: OpenBao ~0.25 GiB, ESO ~0.15 GiB, Authentik server+worker ~1.0 GiB, Authentik PostgreSQL ~0.25-0.5 GiB, cloudflared ~0.05 GiB, i.e. ~1.7-2.0 GiB of the 16 GB host for secrets+identity; defer LDAP and RADIUS outposts (extra pods) until a concrete consumer exists.
- Renovate/pinning list from this research: OpenBao 2.7.1 / chart 0.30.2, ESO 2.11.0, SOPS 3.13.3, age 1.3.2, Authentik 2026.8.3 (chart same), carlpett/sops 1.4.1, OpenTofu 1.13.x, Traefik 3.7.x (>= 3.7.7 for the ExtensionRef namespace fix), cloudflared 2026.9.x.

## Storage and backup

For a single 16 GB Proxmox host running Talos VMs, the storage layer that fits is the Proxmox CSI plugin (v0.20.0, 2026-08-05): a PV is a Proxmox disk (vm-9999-pvc-<uuid>) hot-plugged over the API into whichever Talos VM runs the pod, and it is re-attached automatically when a pod moves to another VM on the same Proxmox node, which is exactly the mobility a 2-worker single-host cluster needs; it costs a scoped API token and ~0.2 GiB RAM instead of Longhorn's 4 vCPU/4 GiB per node or Rook's 3 mons + 2 GiB OSDs, and it avoids democratic-csi's root/sudo SSH credential to the hypervisor. Its snapshots are experimental full copies that need root@pam, so no backup design here may depend on CSI VolumeSnapshots: PVC data goes through VolSync (v0.16.0, restic mover, copyMethod Direct with built-in RWO co-scheduling) and databases through CloudNativePG's Barman Cloud plugin (v0.15.1) because the in-tree barmanObjectStore is deprecated since 1.26 and now scheduled for removal in 1.31.0. Velero (v1.18.4) is a documented non-choice: its node-agent DaemonSet runs root/privileged with no default limits and its cluster-object backup is redundant with Argo CD plus etcd snapshots (talos-backup CronJob, age-encrypted, to S3; restore = wipe EPHEMERAL on control planes and talosctl bootstrap --recover-from). Upstream VolSync has no Kopia mover (PR #1723 closed unmerged July 2026; forks and the alpha Kopiur operator are not "boring"), so restic it is. Proxmox Backup Server 4.2 (2026-04-29, Debian 13.4, S3 datastore backend now officially supported with a documented Cloudflare R2 example) as a Hyper-V Gen2 VM on Node 2 is viable as the second copy: datastore on a fixed VHDX <= 2 TB (Microsoft's Debian limit) formatted ext4/xfs inside the guest so PBS's atime-based GC works, 3-4 GiB fixed RAM, external vSwitch, Secure Boot attempted with the Microsoft UEFI CA template (Proxmox ships a Microsoft-signed shim since PBS 3.1) but disabled as a documented exception if the 2011/2023 CA transition breaks boot. Node 2 is a laptop, so PBS availability is intermittent: schedule vzdump in a known-on window, alert on backup age via a community pbs-exporter (PBS has no native Prometheus endpoint, only InfluxDB), and let PBS sync and S3 upload be the resilient legs. Off-site must be outbound-only because of CGNAT, which all S3/SFTP options satisfy: Backblaze B2 ($6.95/TB-month, free API calls, 3x free egress, S3 Object Lock) is the sensible bulk tier, Cloudflare R2's free tier (10 GB, free egress, but no versioning/Object Lock and incomplete checksum support, plus an open CNPG restore bug #411) suits small egress-heavy sets like etcd snapshots, and a Hetzner Storage Box (~EUR 3.20/mo for 1 TB, SFTP/rsync/restic, server-side snapshots, no S3) is a cheap third option for restic repos but cannot host a PBS datastore. AWS-SDK checksum defaults have broken S3-compatible targets across Loki 3.6/3.7, Barman 3.13 and R2 in 2025-2026, so every S3 client in this design needs an explicit restore test, not just a successful backup. Loki 3.7.8 should run monolithic on a filesystem PV (<= ~20 GB/day, unreplicated by design, Helm caches shrunk from their 8 GiB defaults), with logs explicitly out of backup scope. The main unknowns that gate sizing are Node 1's current contents, the unidentified "additional storage devices", the data volume to protect, Node 2's reliable on-hours and RAM headroom (WSL2 already claims 8 GiB), and the provider/budget choice.

### Design implications

- Default StorageClass = Proxmox CSI on LVM-thin (or ZFS) carved from Node 1's 256 GB SSD, with `pvecm create` to make the single node a one-node cluster, VirtIO SCSI single on every Talos VM, a `kubernetes-csi@pve!csi` privilege-separated token holding only the 5-privilege CSI role (secret SOPS-encrypted in Git), Proxmox CCM for region/zone labels, and `volumeBindingMode: WaitForFirstConsumer`. This is what lets two Talos worker VMs on one host reschedule stateful pods without replication; budget ~0.2 GiB RAM for it versus >=4 GiB/node for Longhorn or >4 GiB for Rook, both of which only replicate data onto the same physical SSD. Keep a second `local-path` class (Talos UserVolume) for caches/scratch only.
- Record an ADR rejecting Longhorn, Rook-Ceph and democratic-csi: Longhorn needs two Talos extensions, a privileged namespace and 4 vCPU/4 GiB per node for replicas that share one disk; Rook needs 3 mons + 2 GiB OSDs and raw devices; democratic-csi zfs-generic would hand the cluster a root/sudo SSH credential to the hypervisor, violating least privilege when an API token with a scoped role (Proxmox CSI) achieves the same result.
- Never build backup or DR on CSI VolumeSnapshots in this cluster: Proxmox CSI snapshots are experimental full copies that require root@pam credentials inside the cluster (which must not be granted). Consequently CNPG must use `method: plugin` (not volumeSnapshot), and VolSync must use `copyMethod: Direct` (RWO co-scheduling handled by VolSync) or `Clone` only where a full-size copy on the 256 GB SSD is acceptable.
- PVC backup tool = VolSync restic mover (v0.16.0, restic 0.18.1): one ReplicationSource per stateful PVC, unique repository path per PVC (`s3:https://s3.<region>.backblazeb2.com/<bucket>/<namespace>/<pvc>`), nightly schedule, retain roughly 7 daily/4 weekly/6 monthly, `pruneIntervalDays` ~14, restic password + S3 keys delivered via ExternalSecrets from OpenBao (bootstrap copies in SOPS). Do not adopt the Kopia fork or Kopiur (alpha, non-upstream); re-evaluate only if backube merges a Kopia mover.
- Velero is a documented non-choice: its node-agent DaemonSet (root, hostPath /var/lib/kubelet/pods, no default limits) and server (512Mi limit) buy little when Argo CD already reconstructs every Kubernetes object from Git and talos-backup covers etcd; this keeps roughly 0.5-1 GiB off the 16 GB host. Revisit only if cross-cluster migration becomes a requirement.
- Databases: CloudNativePG 1.30.x single-instance clusters with requests = limits (start at 512Mi-1Gi, shared_buffers ~25%), backups exclusively via the Barman Cloud plugin v0.15.x (ObjectStore CR per environment, continuous WAL archiving, daily ScheduledBackup with 6-field cron, PITR tested quarterly into a scratch namespace). Phase ordering consequence: cert-manager (Phase 7) is a hard prerequisite of the plugin, so CNPG cannot precede it. Never start on `barmanObjectStore`; it disappears in CNPG 1.31.
- Off-site provider decision: Backblaze B2 is the bulk off-site tier (predictable $6.95/TB-month, free API ops, 3x free egress, S3 Object Lock available for restic/VolSync buckets); Cloudflare R2 is reserved for small, egress-heavy sets that fit the 10 GB free tier (talos-backup etcd snapshots, config exports), given its lack of versioning/Object Lock and its incomplete checksum support. Do not point CNPG at R2 until plugin-barman-cloud issue #411 is re-tested with a full restore in this lab. All of these are outbound HTTPS, so CGNAT is irrelevant for off-site; it only rules out inbound PBS pull from the internet (a future external PBS must use push sync over an outbound WireGuard/Tailscale tunnel).
- Every S3 client in the design gets an explicit, scheduled restore drill, because 2025-2026 AWS-SDK checksum changes broke S3-compatible targets silently in Loki 3.6/3.7, Barman 3.13 and R2: set `AWS_REQUEST_CHECKSUM_CALCULATION=when_required` / `AWS_RESPONSE_CHECKSUM_VALIDATION=when_required` on SDK-based clients talking to R2, pin Loki >= 3.7.x with the aws-chunked fix if it ever uses object storage, and treat 'backup succeeded' as unverified until a restore has run (CLAUDE.md rule 18).
- Second copy / second medium: Proxmox Backup Server 4.2 as a Hyper-V Generation 2 VM on Node 2: 2 vCPU, 3-4 GiB fixed (not dynamic) RAM, 32 GB OS VHDX plus a dedicated fixed-size datastore VHDX of <= 1 TB on F: (Microsoft caps Debian filesystems at 2 TB per VHD), formatted ext4/xfs inside the guest so the atime-based GC safety check passes, Hyper-V checkpoints disabled on the datastore disk, PVE talking to it on port 8007 only. PBS jobs: prune daily, GC weekly (24h5m grace), verify monthly, plus an S3-backed datastore (64-128 GiB cache on the same VHDX) on B2 fed by a sync job as the off-site copy. Attempt Secure Boot with the 'Microsoft UEFI Certificate Authority' template; if the PBS 4.2 ISO does not boot under it, disable Secure Boot for this VM and log the exception with a removal task.
- Node 2 is a laptop, so PBS is an intermittently available target: run vzdump during a user-confirmed on-window, keep PVE backup jobs retrying, alert from Prometheus on `pbs_snapshot_vm_last_timestamp` age > 36 h and failed verifies via a community pbs-exporter (API token with Datastore.Audit), and prefer designs where Node 2 initiates work (PBS pull sync, scheduled S3 upload) so an offline laptop causes a delayed copy rather than a failed one. RAM consequence on Node 2: WSL2's 8 GiB allotment must be lowered (e.g. 4-6 GiB in .wslconfig) while the PBS VM runs.
- Use the idle 2.5GbE direct link (Node 1 TX201 <-> Node 2 UE302C, no switch) as a dedicated backup/storage path by binding a Hyper-V external vSwitch to the UE302C adapter and giving PVE's NIC2 a point-to-point subnet, keeping vzdump/PBS traffic off the 1 GbE LAN; fall back to the dock NIC if the USB adapter misbehaves under Hyper-V. Document this link in the network policy matrix as 'Management/PVE -> PBS:8007 only'.
- Host-level config backup: an Ansible-managed systemd timer on the PVE host running `proxmox-backup-client backup etc.pxar:/etc pve-cluster.pxar:/var/lib/pve-cluster root.pxar:/root --include-dev /etc/pve` with a PBS API token and a client-side encryption key whose passphrase is held in Bitwarden; together with OpenTofu/Ansible in Git this makes the 'rebuild from new hardware' path mostly declarative.
- etcd protection: deploy talos-backup as a CronJob (every 6-12 h) writing age-encrypted snapshots to R2, with the age private key in Bitwarden and SOPS; write docs/runbooks/restore-talos-etcd.md around `reset --system-labels-to-wipe=EPHEMERAL` + `bootstrap --recover-from`, noting that PVs survive because the Proxmox disks persist and Argo CD re-syncs everything else.
- vzdump-to-CIFS (an SMB share on Node 2's F: drive) is kept only as a documented bootstrap fallback for the first full backups before PBS exists: full archives every run, no dedup, so weekly at most; it is retired once PBS is validated.
- Loki: run monolithic (deploymentMode Monolithic, 1 replica) on a 20-50 Gi Proxmox-CSI PV with `loki.storage.type: filesystem`, disable or cap the Helm memcached caches (defaults near 8 GiB would alone exhaust the host), set explicit requests/limits (start 256Mi/1Gi), enable compactor retention, and record the decision that logs are not backed up (unreplicated filesystem store is accepted for this data class).
- Talos disk encryption choice for Proxmox VMs: default to `nodeID` for EPHEMERAL (and STATE) because it protects against disposed/stolen disk images with zero operational dependencies; offer TPM-sealed keys as an optional hardening step requiring OVMF (`efitype=4m`, `pre-enrolled-keys=0`, Talos auto-enroll under virtualization) plus `tpmstate0 version=v2.0`, while documenting that a vTPM's state lives on the same host disk so the gain over nodeID is limited. Reject `kms` (needs an always-on KMS before STATE unlock; chicken-and-egg on a single host) and `static` (key in machine config). Note that host-level encryption of the Proxmox disks is the more meaningful control and belongs in the Phase 2 decision.
- Resource budget line items for Node 1 (16 GB): Proxmox CSI ~0.2 GiB, VolSync controller <0.2 GiB (movers are transient Jobs), CNPG operator + plugin operator + per-instance sidecar ~0.5 GiB before databases, Loki monolithic ~0.5-1 GiB; no PBS VM on Node 1 (docs discourage co-locating and RAM is scarce), so all backup compute lives on Node 2 and in the cloud.

## Observability, CI and Renovate

For this single-host, 16 GB, CGNAT homelab the observability/CI design is constrained more by RAM and by GitHub plan limits than by software maturity. kube-prometheus-stack 91.9.0 (Prometheus Operator v0.94.1, Grafana 13.x subchart, Prometheus 3.15 / 3.13 LTS, Alertmanager 0.34) is current and must be synced by Argo CD with ServerSideApply=true (its CRDs exceed the 262144-byte last-applied annotation); the companion prometheus-operator-crds chart (32.0.1) lets CRDs be a separate, first-wave Application. Prometheus must be deliberately shrunk (60s intervals, retentionSize cap, histogram/kubelet metric drops, local-SSD PVC never NFS); a documented minimal setup reaches ~7k series and <512 MiB. On Talos, three non-obvious requirements apply: Pod Security Admission enforces 'baseline' everywhere except kube-system, so node-exporter/smartctl/hostPath log tailing need a namespace labelled enforce=privileged; controller-manager/scheduler bind to 127.0.0.1 and etcd metrics need listen-metrics-urls (or cert extraction); kubelet serving certs lack IP SANs (chart default insecureSkipVerify=true works, but rotate-server-certificates + kubelet-serving-cert-approver is the clean fix). Logs: Grafana Alloy 1.20 with the GA loki.source.kubernetes component needs no host privileges (DaemonSet must be node-filtered or it tails the whole cluster, GH issue #4787), while Talos machine/kernel logs are JSON-lines over TCP/UDP for which Talos documents Vector/fluent-bit/Filebeat, not Alloy (Alloy's tcplog receiver is experimental). Loki 3.7.8 via the grafana-community chart 18.13.x in Monolithic mode with filesystem storage is the only RAM-sane option; built-in MinIO is deprecated (removal 2026-10-31) and filesystem storage is explicitly unreplicated. Host-side exporters (node_exporter 1.12.1, smartctl_exporter — SMART is invisible inside VMs) come from the prometheus.prometheus Ansible collection 0.30.2; Proxmox is scraped with prometheus-pve-exporter (PVEAuditor token) and OpenWrt with prometheus-node-exporter-lua (2026.06.05 package, 23 collectors, loopback-only by default); PBS has no Prometheus endpoint (InfluxDB push, /status/metrics API since 3.3) but has native Webhook/Gotify/SMTP notifications that should alert on backup failures independently of Kubernetes. Because of CGNAT every alert channel must be outbound-only: native Alertmanager Telegram, ntfy (built-in ?template=alertmanager since 2.14), SMTP, plus a healthchecks.io dead-man's switch for the Watchdog alert. Renovate's hosted Mend app is free for private repos and covers Helm/Kustomize/Argo CD (argocd manager must be explicitly enabled), OpenTofu (*.tofu + registry override), GitHub Actions digest pinning, pre-commit (opt-in), mise tool pins and regex managers for Talos/Kubernetes versions, so Argo CD Image Updater is unnecessary. CI should install pinned tools via mise (mise-action, mise.lock, `mise trust` model) and run one `just ci` recipe locally and in Actions with every action SHA-pinned; the decisive open decision is repository visibility, since on GitHub Free private repos lack enforced rulesets/required status checks, SARIF code scanning and artifact attestations, all of which are free for public repos.

### Design implications

- Argo CD layout: ship Prometheus Operator CRDs as their own Application from the prometheus-operator-crds chart (32.0.1, sync-wave -1) and the kube-prometheus-stack 91.9.0 Application with syncOptions ServerSideApply=true plus annotation argocd.argoproj.io/compare-options: ServerSideDiff=true; set crds.enabled=false in the stack values so CRD upgrades are explicit, reviewable PRs instead of silent Helm no-ops.
- RAM budget on the 16 GB host: size the observability namespace to roughly 1.5-2 GiB total by setting prometheusSpec scrapeInterval/evaluationInterval 60s, retention 15d AND retentionSize (e.g., 15GiB) on a local-SSD PVC (Proxmox local-lvm/local-path, never NFS), dropping histogram buckets and ~90% of kubelet/cAdvisor series via metricRelabelings, disabling unneeded defaultRules groups (windows, kubeProxy when Cilium replaces it, etcd until scraped), single-replica Alertmanager/Grafana, and Grafana without persistence (dashboards as ConfigMaps). Record the measured series count and RSS in docs/observability as the baseline to defend against drift.
- Talos namespace policy: create the monitoring namespace with pod-security.kubernetes.io/enforce=privileged (and document it as the only privileged non-system namespace besides kube-system/cilium) because node-exporter, smartctl (if ever in-cluster) and hostPath log tailing violate Talos' default baseline; keep every application namespace at baseline with a restricted 'warn' and add this exception to the security exceptions register.
- Talos machine config patches needed for complete control-plane scraping (put in talconfig/patches and in the cluster ADR): cluster.controllerManager.extraArgs.bind-address=0.0.0.0, cluster.scheduler.extraArgs.bind-address=0.0.0.0, cluster.etcd.extraArgs.listen-metrics-urls=http://0.0.0.0:2381 (plain HTTP metrics on 2381, reachable only on the servers VLAN), kubelet rotate-server-certificates=true plus the kubelet-serving-cert-approver so metrics-server works and kubelet insecureSkipVerify can later be set false; with Cilium kube-proxy replacement set cluster.proxy.disabled=true and kubeProxy.enabled=false in the chart to avoid permanent dead targets/alerts.
- Pod logs: run Alloy 1.20 (chart 1.13.0) as a DaemonSet using loki.source.kubernetes (GA, no host privileges, no hostPath) with discovery.kubernetes field_selector spec.nodeName=<node> so each pod only tails its own node (avoids the issue #4787 memory blow-up); set explicit requests/limits (e.g., 64Mi/256Mi) since the chart sets none; revisit loki.source.file+hostPath only if kubelet CPU becomes measurable on the 4-core i5-3570.
- Talos machine/kernel logs are JSON-lines over TCP/UDP that Alloy cannot ingest with a GA component; defer them to a later phase and use talosctl logs/dmesg in runbooks, or add a tiny Vector aggregator Deployment (documented by Talos) as machine.logging.destinations target writing to Loki — decide in Phase 11, not now.
- Loki: deploy the grafana-community chart 18.13.x with deploymentMode Monolithic, 1 replica, replication_factor 1, loki.storage.type filesystem on a 20-30 GiB local PVC, schema v13/TSDB, compactor retention ~14-30 days, and limits (ingestion rate, max streams) to protect RAM; set minio.enabled=false (deprecated, removed 2026-10-31). Document that logs are unreplicated and excluded from the 3-2-1 backup scope (acceptable loss) unless an S3-compatible off-site bucket (Cloudflare R2/Backblaze B2) is later adopted as the object store — that change would also make Loki survive a host rebuild.
- Alerting under CGNAT must be outbound-only: use native telegram_config (bot_token_file from a SOPS/ESO-managed Secret, parse_mode HTML) as the primary pager, optionally ntfy via webhook_config to https://ntfy.sh/<topic>?template=alertmanager with a per-topic access token (a self-hosted ntfy would only be reachable from the phone through a Cloudflare Tunnel), and SMTP email (auth_password_file) as the low-priority channel; never rely on anything that needs an inbound port.
- Dead-man's switch: route the chart's built-in Watchdog alert (always firing) to a healthchecks.io check (free, 20 checks) via webhook_config with repeat_interval ~5m; if the heartbeat stops because Node 1, Proxmox, Talos or Alertmanager died, healthchecks pages you by Telegram/email. This is the only way a single-host lab detects its own total outage.
- Backup-path alerting must not depend on the Kubernetes stack: configure Proxmox VE and PBS native notification matchers (SMTP/Webhook/Gotify targets) to send backup/GC/verify/prune failures straight to Telegram/ntfy; treat Prometheus-side backup metrics (pbs exporter or job-last-success pushes) as secondary. PBS has no Prometheus endpoint, so do not plan on scraping it directly; skip InfluxDB entirely (another stateful service on 16 GB is not justified).
- Host exporters via Ansible (prometheus.prometheus 0.30.2): install node_exporter 1.12.1 and smartctl_exporter on the Proxmox host (SMART is invisible inside Talos VMs), bind them to the management/servers VLAN address, firewall them to the Prometheus pod/VLAN source only, and scrape with ScrapeConfig CRDs; run prometheus-pve-exporter (v3.10.1) as an in-cluster Deployment with a dedicated prometheus@pve user, PVEAuditor at '/', an API token with privilege separation disabled, token stored in SOPS/ESO, scraped as /pve?target=<node1 mgmt IP>&cluster=1&node=1.
- OpenWrt: once SSH to the M30 is set up, install prometheus-node-exporter-lua plus -openwrt, -wifi, -wifi_stations, -netstat, -nat_traffic or -nft-counters and -ethtool on the router and both Mi 4A APs (verify package availability for the unknown OpenWrt release first), switch listen_interface from loopback to the management VLAN interface, and add a firewall rule allowing only the Prometheus source; manage the UCI file through Ansible so the exception is in Git.

- Renovate: install the hosted Mend Renovate app (free; 4-hour cadence is ample; no PAT or self-hosted runner to secure) with extends [config:best-practices, :enablePreCommit, :dependencyDashboard, :semanticCommits, :timezone(<confirmed tz>)], enable the argocd manager with managerFilePatterns for the Argo CD Application/ApplicationSet directory, rely on kustomize/helm-values/helmv3 managers for images and charts, add packageRules registryUrls=https://registry.opentofu.org for terraform-provider/terraform-module datasources, let the mise manager bump mise.toml, and add regex customManagers (or github>home-operations/renovate-presets pinned to a tag) for Talos/Kubernetes versions in talconfig.yaml using the '# renovate: datasource=docker depName=ghcr.io/siderolabs/installer' comment convention; automerge only digest/patch updates after a minimumReleaseAge of 3 days and green CI, never majors.
- CI tool strategy: pin every tool once in mise.toml (+ mise.lock) and run the same 'just ci' recipe locally (pre-commit 4.6.2 hooks calling the mise-installed binaries) and in GitHub Actions via jdx/mise-action (SHA-pinned); use marketplace actions only where they add value (trivy-action for DB caching, gitleaks-action v3 for PR comments — no license needed on a personal account, checkov-action v12). Enable the repository setting 'Require actions to be pinned to a full-length commit SHA', set workflow permissions: contents: read, and keep PR lint/scan jobs secret-free so fork PRs are safe; tofu validation uses 'tofu init -backend=false' with no cloud credentials.
- Concrete CI gates: yamllint; helm lint + 'helm template | kubeconform -strict -summary -schema-location default -schema-location <datreeio CRDs-catalog template> -ignore-missing-schemas'; 'kustomize build' each overlay piped to kubeconform; tofu fmt -check/validate; ansible-lint (production profile); shellcheck + shfmt -d; gitleaks (fetch-depth 0) failing the build; trivy config + fs (CRITICAL,HIGH exit-code 1); checkov frameworks kubernetes,helm,kustomize,terraform,dockerfile,github_actions,secrets with SARIF kept as an artifact (code-scanning upload only if the repo is public); semgrep scan --config auto --metrics off --error. Make these required status checks only if the repo is public or on a paid plan (see open question).
- Repository visibility is a design decision, not a preference: on GitHub Free a PRIVATE repo cannot enforce rulesets/required status checks/code owners, cannot upload SARIF to code scanning, cannot use artifact attestations, and burns the 2,000-minute Actions quota; a PUBLIC repo gets all of these free and unlimited minutes. With SOPS/age encryption, no plaintext secrets, and private IP/VLAN details kept generic, a public repo is the standard home-ops practice — but it must be confirmed by the owner before the first push.
- Container images: build with docker/build-push-action v7 (provenance: mode=max, sbom: true) to GHCR, tag with semver AND reference by digest in Kustomize (image: ghcr.io/<owner>/<app>:v1.2.3@sha256:...); if the repo is public add actions/attest-build-provenance v4 with push-to-registry and verify in CI with 'gh attestation verify'; if private, use cosign keyless (cosign-installer v4.1.0) knowing the public Rekor log will expose the repo/workflow identity, or skip signing until visibility is decided. Expect 'unknown/unknown' platform rows in the GHCR UI. Keep images public or add Talos registry auth (machine.registries) for private pulls.
- Do not deploy Argo CD Image Updater: Renovate's docker:pinDigests already turns digest moves into reviewed PRs through the same CI gate, Image Updater adds another controller (RAM) and its docs still scope it to non-critical environments; revisit only if a true continuous-deployment loop for first-party images is wanted later.
- Grafana identity from day one: configure generic_oauth against Authentik (entitlement- or group-based role_attribute_path, role_attribute_strict=true, use_pkce=true, client secret via GF_AUTH_GENERIC_OAUTH_CLIENT_SECRET__FILE from an ESO-synced Secret, signout_redirect_url to Authentik end-session), keep a single break-glass local admin whose password lives only in Bitwarden, and disable local sign-up; expose Grafana externally only via Cloudflare Tunnel + Authentik, never a port forward (impossible under CGNAT anyway).
